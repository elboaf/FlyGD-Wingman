# Cross-platform feasibility: Linux

Research question: can FlyGD Wingman — a Windows-only, tray-resident desktop app for EVE Online multiboxing — be ported to Linux? This file answers twelve questions in priority order, cites a primary source for every claim, and closes with a verdict. A separate inventory, [windows-dependency-inventory.md](windows-dependency-inventory.md), covers the code-level Windows dependencies; this file stays at the platform level. Research snapshot: October 2026 — portal implementations and installer scripts move quickly; re-check anything marked MEDIUM before acting on it.

## Verdict

A Linux port of FlyGD Wingman is **feasible with a scope caveat: target X11 sessions first, treat Wayland as a reduced-feature surface.** The three hardest problems are all the same problem in different clothes — Wayland's security model removes exactly the cross-app primitives Wingman is built on. First, global hotkeys: X11 has XGrabKey, but under Wayland the only sanctioned mechanism is the GlobalShortcuts portal, which KDE and GNOME 48+ implement and wlroots-family compositors do not implement at all (Hyprland ships a private protocol instead, whose anonymous-trigger model inverts how Wingman's keybinds work), leaving evdev/uinput (root-adjacent) as the fallback. Second, per-window capture: the ScreenCast portal does offer per-window PipeWire streams with restore tokens, but every acquisition is a user-confirmed dialog and permissions can be withdrawn, which reshapes the live-preview pipeline from "read pixels on demand" to "negotiate sessions". Third, window enumeration and input injection: there is no Wayland protocol for a client to list or drive other toplevels (xdotool's authors: "unclear if they could ever work"), so client discovery/activation degrades to optional compositor extensions on Wayland while remaining fully solvable via EWMH + XTEST on X11. The fourth real cost is not a display protocol at all: EVE itself runs and multiboxes well under Proton/Lutris (community-supported, not CCP-supported), but the client's settings and gamelogs live inside Wine prefixes whose locations vary by install method, so path discovery and prefix probing become user-visible features. The easy wins are the plumbing: pywebview supports Linux (GTK/Qt), pystray has Linux backends, autostart becomes a `.desktop` file drop, single-instance becomes a D-Bus name, and the Rust settings-codec sidecar cross-compiles with a standard `--target` flag. WebView2 is the one hard wall — Microsoft has closed the Linux request as not planned — but it is a wall pywebview was designed to route around.

## 1. pywebview on Linux

pywebview officially supports Linux through two interchangeable GUI toolkits: GTK (via PyGObject with WebKit2GTK) and Qt (PyQt5/PyQt6, PySide2/PySide6). The project README states: "_pywebview_ is available for Windows, macOS, Linux (GTK or QT) and Android. It uses native GUI for creating a web component window: WinForms on Windows, Cocoa on macOS and QT or GTK on Linux" ([pywebview README](https://github.com/r0x0r/pywebview/blob/master/README.md)). On Linux the extra is mandatory, not automatic — `pip install pywebview[gtk]` or `pip install pywebview[qt]`; the GTK route needs `python3-gi`, `gir1.2-gtk-3.0`, `gir1.2-webkit2-4.1` and WebKit2 version 2.22 or greater ([pywebview installation guide](https://github.com/r0x0r/pywebview/blob/master/docs/guide/installation.md)). The GUI can be forced with the `gui` argument of `webview.start()`; the project's own AGENTS.md records a `guiversion` argument used to pick WebKit2GTK versions, and the codebase sets `guiversion` for the GTK GUI ([pywebview AGENTS.md](https://github.com/r0x0r/pywebview/blob/master/AGENTS.md)).

Consequences for Wingman's UI stack:

- **JS bridge**: the two-way JavaScript–Python communication and the built-in HTTP server are headline features on every supported OS ([pywebview README](https://github.com/r0x0r/pywebview/blob/master/README.md)), so the `WM.send()` → `pywebview.api.<method>` half and `_push` half should carry over. This matches the architecture note that per-backend behaviour differences are documented in the API reference by a `guiversion` note rather than being absent ([pywebview AGENTS.md](https://github.com/r0x0r/pywebview/blob/master/AGENTS.md)).
- **Frameless windows**: Wingman's window is frameless. Frameless support is implemented per GUI backend, and pywebview's issue tracker carries long-standing GTK/Qt frameless gaps (e.g. resizing behaviour and window dragging differ from the WinForms/WebView2 path). Confidence MEDIUM on backend parity: pywebview's docs no longer publish a per-platform support matrix (the support page renders a generic feature grid — [docs/.vuepress/components/Features.vue](https://github.com/r0x0r/pywebview/blob/master/docs/.vuepress/components/Features.vue)); the [API reference](https://pywebview.flowrl.com/2.x/docs/API.html) documents `frameless`/`easy_drag`/`pywebview-drag-region` without Linux exclusions, so "which of our frameless behaviours degrade" needs a smoke pass of the actual UI rather than a doc lookup. Wingman's own resize-border chrome (`ui/chrome.py`) subclasses WndProc and would be rewritten per-backend regardless.
- **Transparency**: same caveat — not confirmed from a primary source in this pass.
- **Renderer change**: moving from WebView2 (Chromium) to WebKit2GTK (WebKit) or QtWebEngine means a different browser engine for the ES5 UI. Risk is low for a no-framework HTML/CSS/ES5 UI, but rendering/feature differences (fonts, CSS subpixel behaviour, `window.<handler>` push mechanics) need a smoke pass. Qt's two renderer options are explicitly versioned in the install docs: QtWebChannel/QtWebEngine ("more modern, preferred") vs QtWebKit ("legacy, but available for more platforms") ([pywebview installation guide](https://github.com/r0x0r/pywebview/blob/master/docs/guide/installation.md)).

Rating: GOOD with a MEDIUM-confidence frameless caveat. Confidence HIGH on backends and install deps (primary sources above), MEDIUM on per-feature deviations.

## 2. WebView2 Runtime on Linux

Not available. The official distribution documentation scopes the Evergreen and Fixed Version runtimes to Windows 10 and Windows 11 devices and describes Windows-only deployment (registry detection under `HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate`, per-machine/per-user Windows installers) with no non-Windows platform mentioned anywhere on the page ([Distribute your app and the WebView2 Runtime — Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)). The feature request for Linux support in Microsoft's own tracker ([WebView2Feedback issue #645](https://github.com/MicrosoftEdge/WebView2Feedback/issues/645), opened November 2020, 218 👍 reactions) is **closed as not planned** with the `priority-low` label and the closing note "We have considered this issue and decided that we will not be able to address it in the near future"; the sibling request [#1423](https://github.com/MicrosoftEdge/WebView2Feedback/issues/1423) asks for "other platforms like Linux" and remains the tracker's proxy for that outcome.

For Wingman this means the Linux port necessarily replaces the WebView2-based GUI backend with pywebview's GTK or Qt backend; there is no "WebView2 under Wine" path worth engineering (WebView2 inside a Wine prefix is possible in principle but is documented only as community hacking, e.g. running Windows WebView2 apps in Bottles — not a supportable foundation). Confidence HIGH.

## 3. Global hotkeys on Linux

Wingman's `HotkeyEngine` supervises a bundled AutoHotkey script; AHK is Windows-only, so global hotkeys are a genuine port. Two regimes:

**X11 — works, with the usual X caveats.** pynput uses X (requires an X server and `$DISPLAY`; over SSH you must set `DISPLAY=:0` yourself) or root/uinput ([pynput platform limitations](https://pynput.readthedocs.io/en/latest/limitations.html)). Global hotkeys under X are XGrabKey-based; under Wayland, pynput's docs say the X server emulator Xwayland "will usually run, providing limited functionality. Notably, you will only receive input events from applications running under this emulator" — i.e. global hotkeys effectively do not work for native Wayland windows.

**Wayland — no client key grabs; the answer is the GlobalShortcuts portal.** The [org.freedesktop.portal.GlobalShortcuts](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html) portal "lets applications create global shortcuts sessions, and register shortcuts to them. These shortcuts are activated regardless of the focused state of the application window", with `BindShortcuts` presenting a compositor dialog where the user confirms/configures triggers, and `Activated`/`Deactivated` signals carrying `activation_token`s for focus-stealing prevention. Compositor support is the catch:

- **KDE Plasma: yes.** KDE's portal file advertises GlobalShortcuts, as the GNOME feature-request thread notes ("Note that KDE does seem to advertise support for this portal", linking [kde.portal](https://invent.kde.org/plasma/xdg-desktop-portal-kde/-/blob/master/data/kde.portal)) ([GNOME Discourse feature request](https://discourse.gnome.org/t/feature-request-globalshortcuts-portal/15343)).
- **GNOME: yes since GNOME 48 (released March 2025)** — xdg-desktop-portal-gnome 48.0 implements GlobalShortcuts (GNOME help threads confirm the implementation lives in xdg-desktop-portal-gnome, receiving input from the shell — [discourse](https://discourse.gnome.org/t/how-do-you-enable-disable-global-shortcuts-in-gnome-48/29119)); the feature request sat open from 2020 and GNOME 45–47 systems demonstrably lacked it ([t3-code issue](https://github.com/pingdotgg/t3code/issues/12589)). Confidence MEDIUM on the exact version cutoff.
- **wlroots-based compositors: no portal backend implements it.** xdg-desktop-portal-wlr (the wlroots backend) does not implement GlobalShortcuts; a user report on niri (wlroots-family) shows the failure mode: the only installed portal backend (xdg-desktop-portal-gnome) "expects GNOME Shell and cannot service global shortcuts on niri. No niri/hyprland backend exists (xdg-desktop-portal-wlr does not implement the portal)" ([hermes-agent issue #82654](https://github.com/NousResearch/hermes-agent/issues/82654)).

**Hyprland is the strongest Wayland case study — and it inverts the model.** Hyprland (the compositor under Omarchy, DHH's Arch-based distro) ships its own private global-shortcuts protocol, [hyprland-global-shortcuts-v1](https://wayland.app/protocols/hyprland-global-shortcuts-v1) ([source XML](https://github.com/hyprwm/hyprland-protocols/blob/main/protocols/hyprland-global-shortcuts-v1.xml)). No kernel module is involved anywhere: the compositor is the one userspace process holding the privileged input seat via libinput/evdev, and the protocol is an ordinary Wayland extension on top of that. But its registration request bakes in a model inversion that matters for Wingman: "a global shortcut is anonymous, meaning the app does not know what key(s) trigger it. The shortcut's keybinding shall be dealt with by the compositor." The user binds keys in compositor config and the app receives opaque `pressed`/`released` events — the opposite of Wingman's bookmark-keybind UX, where Wingman defines, captures and displays the keys. The injection half exists as the `hyprctl dispatch sendshortcut` dispatcher, but it is dispatcher-grade, not protocol-grade: it reports "ok" even when the target application never receives the key ([Hyprland issue #6576](https://github.com/hyprwm/Hyprland/issues/6576), closed as not planned). Omarchy's own hotkeys are plain Hyprland binds in compositor config ([Omarchy hotkeys manual](https://github.com/omacom/omarchy/blob/master/manual/07-hotkeys.md)) — even the friendliest Wayland desktop means the app plays on the compositor's terms.

**Prior art for cross-app input tools** is instructive: xremap "uses `evdev` and `uinput`, which works whether you use X11 or Wayland", requires root or uinput-group permissions or a compositor-specific integration mode, and ships "full" and "minimal" variants precisely because desktop integration varies ([xremap README](https://github.com/xremap/xremap), [xremap troubleshooting](https://github.com/xremap/xremap/blob/master/doc/troubleshooting.md)).

For Wingman: X11 gives a near 1:1 port (XGrabKey ≈ RegisterHotKey); Wayland requires the GlobalShortcuts portal where available (KDE, GNOME 48+) or a per-compositor private protocol (Hyprland's, which makes shortcuts anonymous — the app never learns its own trigger keys), and has **no solution at all on wlroots compositors** short of evdev/uinput elevation or per-compositor plugins. The bookmark keybinds feature would need a runtime backend choice: X11 XGrabKey, portal where offered, evdev/uinput fallback documented as root-y. Confidence HIGH.

## 4. Per-window capture of another app under Wayland

**X11: fine.** XShm/XGetImage can read any window's pixels directly; this is the mechanism Wingman's preview pipeline would keep on X11.

**Wayland: the only sanctioned path is the ScreenCast portal via PipeWire.** The [org.freedesktop.portal.ScreenCast](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html) portal does support per-window sources: `AvailableSourceTypes` is a bitmask where `2: WINDOW` ("Share application windows") sits alongside `1: MONITOR`; `SelectSources(types=…, multiple=…)` and `Start()` "typically present a dialog to the user", whose response is a list of PipeWire streams with node id, position, size and `source_type`. Frames arrive over `OpenPipeWireRemote()`'s file descriptor, not as a pixel API.

For Wingman's live per-client previews the important clauses are the session-persistence ones: `persist_mode` (0 = do not persist, 1 = while the app runs, 2 = until revoked) and `restore_token` — "If the stored session cannot be restored, this value is ignored and the user will be prompted normally. This may happen when, for example, the session contains a monitor or a window that is not available anymore, or when the stored permissions are withdrawn. The restore token is invalidated after using it once." So multiboxing N EVE clients means either N user-confirmed window streams per session restore (one `Start()` dialog each, unless `multiple` sources are selected in one dialog) or one restore chain per client, each single-use token requiring refresh logic. There is no silent re-attach by design: a permission prompt on every stream acquisition is the portal's normal behavior, and withdrawal by the user is an expected event, not an error.

Compositor-side caveats: GNOME/Mutter implements the portal through xdg-desktop-portal-gnome (Mutter-backed), so window streams exist on GNOME; on wlroots compositors the stock xdg-desktop-portal-wlr backend covers monitor capture, and window capture depends on compositor-specific backends or newer adoptions — a niri discussion records that xdg-desktop-portal-gnome is "the only feature-rich screencasting portal with an intuitive UI" while portal-wlr "only supports sharing the entire" output ([niri discussion #3085](https://github.com/niri-wm/niri/discussions/3085)). Confidence HIGH on the portal contract (primary spec above), MEDIUM on the per-compositor matrix (community threads, not vendor matrices).

## 5. Enumerating other apps' windows and sending synthetic input

**X11: fine, this is solved technology.** Window enumeration is the EWMH `_NET_CLIENT_LIST` root-window property maintained by the window manager ([EWMH spec](https://specifications.freedesktop.org/wm-spec/latest/)); synthetic input is XTEST — the mechanism xdotool uses ("simulate keyboard input and mouse activity, move and resize windows… using X11's XTEST extension and other Xlib functions"), which also covers per-window activate/geometry via Xlib calls ([xdotool README](https://github.com/jordansissel/xdotool)). This is functionally what Wingman's preview discovery and client-activation code does against Win32 today.

**Wayland: no core protocol for either half.** The stable Wayland core protocol (`wayland.xml`) contains no requests by which a client can list other clients' toplevels or inject input into another client's surfaces — the [protocol index](https://wayland.app/protocols/wayland) shows such capability only as optional extensions: `ext-foreign-toplevel-list` (staging; a read-only listing of foreign toplevels), `wlr-foreign-toplevel-management` (wlr-family; activate/minimize with compositor consent), plus compositor-specific input protocols (`wlr-virtual-pointer`, `kde-fake-input`). xdotool's Wayland section is the canonical statement of the gap: "Typing, window searching, and many other functions of xdotool do not work, and it is unclear if they could ever work", pointing to uinput-based ydotool and dotool as the alternatives ([xdotool README, Wayland section](https://github.com/jordansissel/xdotool)).

Consequence for Wingman: the discovery→activate→hotkey cycle can be ported for X11 sessions nearly as-is (Xlib + EWMH + XTEST via python-xlib or a small C helper). Under Wayland, per-window targeting degrades to whatever the running compositor exposes (foreign-toplevel extensions on wlr/KDE, nothing standardized on GNOME beyond portal-mediated capture), and global input injection becomes a root/uinput design. Confidence HIGH.

## 6. EVE Online on Linux

**Official stance: Linux is not a supported platform.** Lutris lists EVE's platforms as "Macintosh, Windows" ([Lutris: EVE Online](https://lutris.net/games/eve-online/)), and CCP's support knowledge base carries no Linux install path — the community fills that gap (the EVE Online Forums maintain a [Linux category](https://forums.eveonline.com/c/technology-research/linux/77) and an [Installing EVE with Wine guide](https://forums.eveonline.com/t/installing-eve-with-wine-guide/122711)). I could not retrieve a specific support.eveonline.com "unsupported OS" article during this pass; treat the exact official wording as unverified (confidence MEDIUM on that one citation, HIGH on the substance — CCP ships Windows and Mac clients only). On anti-cheat, the closest official-on-record statement (via GamingOnLinux, about EVE Vanguard) is: "EVE Vanguard has supported Easy Anti-Cheat on Linux for approximately the past two years, and members of our community have been playing successfully via compatibility layers. While we haven't conducted dedicated testing on SteamOS and don't currently have plans for a native Linux client" ([GamingOnLinux, Sep 2026](https://www.gamingonlinux.com/2026/09/extraction-shooter-eve-vanguard-starts-alpha-in-november-linux-supported-with-the-anti-cheat/)). EVE Online itself is known to run without kernel anti-cheat interference under Wine; the practical evidence is the thriving install base.

**Installer status.** Lutris carries a maintained community installer — "Wine, July 2026 Launcher version, last published 2 months ago" — which installs an older stable launcher (1.9.4) and then upgrades to CCP's latest, requiring GE-Proton; the install notes document an active cat-and-mouse with recent launcher web-view regressions ("As of Mid-June 2026, Version 1.15.3 does not launch correctly through Lutris") ([Lutris: EVE Online](https://lutris.net/games/eve-online/)). Steam/Proton is the smoother path: the EVE University guide's verdict is "In our experience the easiest is to play EVE Online on Steam… Multiboxing (running multiple clients) also works great", with a concrete Proton recipe (Proton Experimental, `PROTON_NO_ESYNC=1 PROTON_NO_FSYNC=1`) ([EVE University wiki: Installing EVE on Linux](https://wiki.eveuniversity.org/Installing_EVE_on_Linux)). Multiple clients under Wine multibox fine — this is also why the wiki points multiboxers at sxhkd for client switching.

**Where gamelogs/settings live in a prefix.** Per the E-UNI wiki, with Steam the client settings live at `~/.steam/steam/steamapps/compatdata/8500/pfx/drive_c/users/steamuser/AppData/Local/CCP/EVE/c_ccp_eve_tq_tranquility/` ("can be manipulated the same as in windows"), and with Lutris the prefix layout is `~/Games/eve-online/drive_c/users/$USER/AppData/Local/eve-online/` ([EVE University wiki](https://wiki.eveuniversity.org/Installing_EVE_on_Linux)). The logs tree (`Documents/EVE/logs`) follows the same rule — inside the prefix at `drive_c/users/<user>/Documents/EVE/logs` — but that specific path is community-evidenced rather than confirmed from a primary source in this pass: confidence MEDIUM. Either way the port's path-discovery problem changes shape: on Windows Wingman globs real user profiles; on Linux it would probe known prefix layouts (Steam compatdata, Lutris, manual Wine prefixes) for `drive_c/users/*/…`.

Rating: the game itself runs, multiboxing included; the port's EVE-specific risk is not the game but prefix-dependent path discovery and launcher-version churn (the Lutris installer's June 2026 breakage is a representative example). Confidence HIGH on multiboxing/paths, MEDIUM on the exact CCP support-page wording.

## 7. pystray on Linux

pystray supports Linux through three backends, selected automatically or forced via `PYSTRAY_BACKEND` ([pystray usage docs](https://pystray.readthedocs.io/en/latest/usage.html)):

- **appindicator** — "the preferred choice. All pystray features except for a menu default action are supported"; falls back to ayatana-appindicator when the appindicator library is absent. Works over DBus (StatusNotifierItem), so it is the natural backend under Wayland sessions (KDE and GNOME-with-extension support it).
- **gtk** — "All pystray features are available, but it may not actually result in a visible icon: when running a gnome-shell session, a third party plugin is required to display legacy tray icons."
- **xorg** — the legacy X11 fallback; the docs state plainly that "Menus are not supported on X", notifications are "not supported on macOS and Xorg", and menu default items behave differently on X ("On X, this is the only action available").

Runtime feature detection is an explicit API contract: `Icon.HAS_MENU`, `HAS_MENU_RADIO`, `HAS_DEFAULT`, `HAS_NOTIFICATION` must be checked rather than assumed — a clean pattern for Wingman, whose tray menu currently assumes full Win32 behaviour (all features available on the win32 backend). Two caveats for the port: GNOME's stock shell shows AppIndicator icons only with an extension installed (upstream pystray documents this for the gtk backend's legacy path), and under Wayland there is no X-org tray — the appindicator/DBus route is the only one that reliably renders. Confidence HIGH.

## 8. EVE client settings/gamelog path discovery on Linux

Wingman's Windows discovery is two environment-variable walks: `%LOCALAPPDATA%\CCP\EVE` for the settings tree (`wingman/evesettings/tree.py` already carries a `~/.local/share/CCP/EVE` fallback branch for non-Windows platforms) and `%USERPROFILE%\Documents` (+ the OneDrive-redirected variant) for gamelogs (`wingman/combatlog.py`). On Linux neither location is stable, because EVE runs inside a Wine prefix whose location depends on how the user installed the game:

- **Steam/Proton:** the prefix is per-appid compatdata — per the E-UNI guide, `~/.steam/steam/steamapps/compatdata/8500/pfx/drive_c/users/steamuser/AppData/Local/CCP/EVE/c_ccp_eve_tq_tranquility/` for settings ([EVE University wiki](https://wiki.eveuniversity.org/Installing_EVE_on_Linux)). The `8500` appid and the `steamuser` profile name are the stable parts; the `~/.steam` root can also be `~/.local/share/Steam` depending on install style.
- **Lutris:** the guide's own recipe uses `~/Games/eve-online/drive_c/users/$USER/AppData/Local/eve-online/` ([EVE University wiki](https://wiki.eveuniversity.org/Installing_EVE_on_Linux)); Lutris also supports arbitrary prefix paths, so discovery must read Lutris config rather than assume.
- **Plain Wine:** the default prefix `~/.wine/drive_c/users/$USER/…` mirrors the Windows layout one level down the prefix root.

So the port's discovery becomes prefix probing: a candidate list (`~/.steam/steam/steamapps/compatdata/*/pfx`, `~/Games/*/`, `~/.wine`, plus prefixes named in Lutris config) each walked for `drive_c/users/*/AppData/Local/CCP/EVE` and `drive_c/users/*/Documents/EVE/logs`. Mechanically this is the same globbing code with a different root list — no new subsystem, but more user-visible failure modes (multiple prefixes, custom locations) that the Browse… fallback (`ui/api.py` already offers one for redirected Documents) must absorb. Confidence MEDIUM — prefix layouts are community-evidenced (E-UNI wiki, Lutris installer script) rather than documented by CCP.

## 9. XDG autostart

Wingman's Windows autostart (registry Run key / shortcut management in `autostart.py`) maps to the [Desktop Application Autostart Specification](https://specifications.freedesktop.org/autostart-spec/latest/): "By placing an application's .desktop file in one of the Autostart directories the application will be automatically launched during startup of the user's desktop environment after the user has logged in." The directories are `$XDG_CONFIG_DIRS/autostart` (user default `~/.config/autostart/`, system default `/etc/xdg/autostart/`), the file is a [desktop entry](https://specifications.freedesktop.org/desktop-entry-spec/latest/) (`Type=Application`, `Exec=…`), and the spec defines the toggling semantics Wingman would implement: a same-named user file with `Hidden=true` disables a system-wide entry, `OnlyShowIn`/`NotShowIn` scope by desktop environment, and `TryExec` skips the entry when the binary is missing. This is a file drop plus a `Hidden` flag flip — a strictly simpler contract than the Windows side. Confidence HIGH.

## 10. Single-instance convention

Wingman's Windows mechanism is kernel mutexes (the new mutex plus `LEGACY_MUTEX_NAME`, which stops 3.x and 4.0 running at once). The canonical Linux convention is ownership of a well-known D-Bus session-bus name: GApplication documents exactly this — "If given [a unique application ID], only one application with this ID can be running at a time per session… When your application is launched again, its arguments are passed through platform communication to the already running program… On Linux, the D-Bus session bus is used for communication" ([Gio.Application — docs.gtk.org](https://docs.gtk.org/gio/class.Application.html)). A plain lockfile under `$XDG_RUNTIME_DIR` (per the XDG base directory specification) is the accepted fallback for apps that do not want the GIO dependency; it is what most non-GTK single-instance implementations do. Note the scope difference from Windows mutexes: D-Bus names and `$XDG_RUNTIME_DIR` are per-session/per-user, so they prevent duplicate instances within one login but do not, by themselves, reserve the name across users the way a `Global\` mutex can — for Wingman the per-session scope matches actual usage (one user, one EVE session). A Flatpak sandboxed app "can only own its own name on the bus" by default ([Flatpak sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)), which is compatible with this scheme as long as the application ID matches the Flatpak ID. Confidence HIGH.

## 11. Python GUI packaging for Linux end users

For a Python app with native deps (PyGObject/WebKit2GTK, PipeWire client) the realistic options are: **venv/pipx + distro packages** — cheapest to build, but the user must satisfy native deps (WebKit2GTK ≥ 2.22 per pywebview's install guide, section 1) and gets no app menu entry without extra packaging; **deb/rpm** — native integration but per-distro maintenance burden; **AppImage** — one self-contained file ([appimage.org](https://appimage.org/)), no sandbox, simplest distribution outside stores, but no update story and bundling GTK+WebKit2GTK is large and glibc-sensitive; **Flatpak** — builds against the freedesktop/GNOME runtime so the WebKit2GTK version problem disappears, ships the .desktop/desktop-entry integration (section 9) for free, and is the only option that plays well with Flathub-style distribution. The sandbox is the price: by default "no access to any host files except the runtime, the app, `~/.var/app/$FLATPAK_ID`…", no network, no device nodes, "limited access to the session D-Bus instance — an app can only own its own name on the bus", and "no access to host services like X11"; grants are static `finish-args` (`--share=network`, `--device=dri`, `--socket=wayland` + `--socket=fallback-x11` being the documented pairing for apps that should work on both session types) ([Flatpak sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)). For Wingman specifically: portal access (`org.freedesktop.portal.*`) survives the default D-Bus filter, so the ScreenCast/GlobalShortcuts path works from a sandbox — but raw X11 capture of EVE windows, evdev/uinput input injection and file-system probing of arbitrary EVE prefixes (`~/Games`, `~/.steam`, `~/.wine`) each need explicit, reviewable permissions that a Flathub reviewer would push back on. That pushes the first Linux build toward AppImage-or-untarred-venv with Flatpak as a later hardening step. Confidence HIGH on Flatpak facts (primary docs above), MEDIUM on the AppImage bundling-effort judgement.

## 12. Rust sidecar cross-compile

Confirmed standard practice. `cargo build` takes `--target <TRIPLE>` under Target Selection, and `--target-dir` controls the output directory ([cargo build — The Cargo Book](https://doc.rust-lang.org/cargo/commands/cargo-build.html)); building with `--target x86_64-unknown-linux-gnu` is the normal way to produce a Linux binary of the settings-codec sidecar. Two deployment notes: cross-compiling *from* a Windows host needs a cross toolchain/linker (typically done from CI on a Linux runner instead, where it is a plain native build — the repo's CI already runs `cargo test` on ubuntu), and glibc matters: a binary built on a newer distro requires a matching-or-newer glibc on the user's machine, which is one of the classic arguments for shipping via Flatpak/AppImage/manylinux-style base images (see section 11). Confidence HIGH.
